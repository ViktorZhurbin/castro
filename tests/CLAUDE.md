# Testing

Six layers across two runners, the last one manual, plus one repo-wide guard test that sits outside the layer model. A new test belongs in the cheapest layer that can catch its regression.

| What it pins                                                     | Lives in                                                                   | Run by                                |
| ---------------------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------- |
| Pure functions and single modules, no DOM or built site          | `core/src/**/*.test.js`                                                    | `bun test`                            |
| The client runtime against a DOM                                 | `core/src/islands/castroIsland.test.js`, `core/src/dev/liveReload.test.js` | `bun test`                            |
| A real site's build output                                       | `tests/site/`, `tests/site-srcdir/`                                        | `bun test:site`                       |
| Terminal error output, per-scenario fixtures covering every code | `tests/errors/`                                                            | `bun test:errors`                     |
| Code that must _not_ compile                                     | `tests/site/types/islandContracts.tsx`                                     | `bun check:code` — **not `bun test`** |
| The error overlay in a browser                                   | —                                                                          | by hand                               |

A code can have more than one fixture in row 4 — `BUNDLE_FAILED` has four, `NO_DEFAULT_LAYOUT` has three — when distinct scenarios produce it; the row guarantees every code is covered, not that coverage is 1:1.

`bun test:site` and `bun test:errors` scope to their own fixture directories, for iterating on one layer without paying for a full run. Rows 1, 2, and the repo-wide guard test below have no scoped script — only bare `bun test` (aliased `bun test:all` inside `verify`) reaches them. The fifth row is the trap, since a green `bun test` never executes it. So: a pure function gets a `*.test.js` beside it, anything needing built HTML goes in `tests/site/`, anything needing stderr becomes a `tests/errors/` fixture (recipe in that directory's README), and a rule that must be rejected at compile time goes in `islandContracts.tsx`.

Two guard tests keep this documentation honest rather than aspirational, by checking the model itself rather than pinning a layer. `tests/preact-range.test.js` fails when any manifest's Preact range drifts from `core`'s peer dependency — a repo-wide invariant, not a build layer, so it has no table row above and no scoped script; only bare `bun test` reaches it. `tests/errors/error-goldens.test.js` lives inside row 4 and runs under `bun test:errors` with the rest of that directory, but carries an extra assertion keeping `tests/errors/README.md`'s fixture table honest — mechanism there.

`bun test:site` builds and verifies `tests/site/`, which exercises the full pipeline with Preact islands (all directives, multiple islands per page, CSS modules, component composition, signals, and one island nested under `components/ui/` that pins nested bundle URLs — don't flatten it). The site mirrors a real project's structure — **use it as the reference for expected patterns** when you're unsure how something should be wired up. That is the one thing it owns over `website/`, which is the demo playground and holds the canonical tsconfig. It also builds and verifies `tests/site-srcdir/`, a minimal fixture pinning the `srcDir` output contract — the only place in `tests/` that sets `srcDir`.

`build-output.test.js`'s last section pins the hydration seam: the marker attributes the build emits, matched against `dist/castro-island.js` — the runtime is only ever read as text there, so this catches a rename on either side but never proves an island actually hydrates. That proof lives in `core/src/islands/castroIsland.test.js` and `core/src/dev/liveReload.test.js`, which register a `happy-dom` `Window` on `globalThis` and drive the real runtime: directive branch selection (`comrade:eager`/`comrade:patient`/`comrade:visible`), the `hydrate()` path including a failed dynamic import, and the error-overlay markup. The browser overlay still isn't exercised against a live dev server — that stays manual.

`happy-dom` was declined once as a second execution environment not worth 334 readable lines; it was taken when both runtimes changed substantially and the first pass found `castroIsland.js` marking an island `ready` whose module exported no mounting function.

Sites are type-checked by `bun check:code`, which is load-bearing rather than incidental: hydration directives are typed `true` (not `boolean`), so `comrade:eager={false}` is rejected at compile time instead of being reinterpreted at runtime. `tests/site/types/islandContracts.tsx` holds `@ts-expect-error` pins for that rule and for islands-reject-children; it is never built, and a loosened rule surfaces as an unused-directive error.

`bun test:errors` covers the terminal renderer only, which is why the browser overlay stays its own row above — regenerating goldens and verifying the overlay by hand are both covered in `tests/errors/README.md`.

Every fixture site here carries its own package.json, and each one pins the same Preact range as `core/package.json` — see the peer-dependency decision in the root CLAUDE.md before changing one.

## Known gaps, left open on purpose

- **`core/src/dev/server.js`'s `hasFileChanged` tests pin the predicate's logic, not the FSEvents rebuild loop** — that loop is unreproducible on Linux either way, so a green suite there doesn't prove the macOS self-rebuild guard works end to end.
- **`watchDir` and `startDevServer` are closure-scoped and untested.** Measured, not assumed: inverting the `!` in `if (!(await hasFileChanged(...))) continue;`, or deleting that line outright, leaves the whole suite green. Covering it means extracting the watch loop from the `for await`, which buys much less than the fetch-handler extraction did. What's left uncovered is the loop itself, not the rebuild path: its other dependency is content-hashed module paths, and those are pinned in `core/src/utils/cache.test.js` — a constant hash there leaves every other test green while the dev server serves stale modules.
- **`tests/site/build-output.test.js` builds once in `beforeAll`**, so a regression that makes the build throw aborts the whole file as a single failure — individual tests never run. Coverage of a build-time guard therefore comes from the _fixture existing_, not the assertion. This is why the `{null}`/`{undefined}` island children in `pages/comrade-eager.tsx` are load-bearing: mutation testing confirmed that narrowing the guard to reject `null` escapes the suite without them, and is caught by the build failing with them. Don't delete a fixture because its assertion looks redundant. The stale file that `beforeAll` plants in `dist/` before building is load-bearing the same way — it is the whole of the output-dir wipe's coverage, and writing it before the build is what keeps one build enough to observe the wipe.
- **Not tested at all, on purpose** (filtered against "Two Forces" in the root CLAUDE.md — testing these would assert the opposite of intended behavior): output-path collisions, dev-server input hardening (`/%ZZ`, traversal), dead-island elimination, production concurrency, runtime config validation, cross-platform paths. Also rejected: a coverage-percentage gate — in a repo whose default is to delete code that merely survives an edge case, a ratchet incentivizes exactly the tests that rule wants gone. `bun test --coverage` as a one-time diagnostic to locate seams is fine, but read it knowing that rows 3 and 4 spawn `castro build` as a subprocess — none of that execution is attributed. `compiler.js` reads 5%, `registry.js` and `layouts.js` 18%, all three exercised on every run, which leaves a genuinely uncovered file indistinguishable from them. Only the in-process rows' numbers mean anything.

## Working practice for new tests

Write the test, then break the code it covers and confirm it goes red. Also confirm whether a pre-existing test already catches the same mutation — if one does, the new test may not be adding what it claims. A test that cannot go red is worth less than the lines it costs. Three lessons worth repeating:

- **Mutate the branch that _does_ something, not just the skips.** In `hasFileChanged`, the mutation that mattered was the `catch`: a failed stat means the file was deleted and must **still** rebuild, so `catch { return false }` silently stops deletions from rebuilding — a user-visible regression that the obvious early-return mutations leave green.
- **A green mutation can expose a weak pre-existing test.** Deleting the containment check in `resolveStaticFile` survived the whole suite, because `/` finds `dist/index.html` before it ever reaches the `dist.html` sibling — the assertion that claimed to cover it passed on candidate order alone. It took a second fixture whose output dir has no index to reach the check at all.
- **A surviving mutation sometimes means the code should go, not that a test is missing.** Deleting the explicit `Content-Type: text/html` from the 404 response changed nothing observable, because Bun infers the type from the extension — and the explicit spelling was actually dropping the charset the inference includes. The fix was to delete the header and assert the inferred outcome, not to pin a redundant line.
